Android app release checklist.

Use this checklist before publishing or sharing a new Android app version.

Release guidePractical checklist

1. Confirm the release scope

Write down what changed in this version. Separate new features, bug fixes and known limitations. Make sure the release build contains only the features and configuration intended for users.

2. Test real user journeys

  • Install the app on a clean device or emulator.
  • Test sign-up, login, logout and password recovery if available.
  • Test the main feature from beginning to end.
  • Check empty states, invalid input, slow internet and offline behavior.
  • Test on more than one screen size and supported Android version.
  • Verify app updates over the previous version.

3. Review permissions and privacy

Confirm that every requested permission is necessary and used as described. Check the privacy policy against the app's actual data collection, sharing, retention and deletion behavior. Do not claim that data is encrypted, never shared or deleted unless the implementation really supports that claim.

4. Check app identity and versioning

Verify the application ID, app name, launcher icon and version information. Increase the version code for each new Android release and use a clear version name that users can understand.

5. Protect the release build

Build a release variant rather than sharing a debug build. Protect signing keys and passwords; do not commit them to a public repository. Keep a secure backup of the signing material and document who can access it.

6. Inspect the final package

Install the exact APK or app bundle you plan to distribute. Confirm that it opens, connects to required services, displays the correct branding and does not expose debug menus or test credentials. Check the package size and remove unused assets where practical.

7. Prepare release information

Write concise release notes that explain user-visible changes. Provide accurate screenshots, support contact information and a working privacy-policy link wherever the distribution channel requires them.

8. Monitor after release

After publishing, monitor crash reports, user feedback and support messages. Have a rollback or hotfix plan for serious problems. Record the released version and the source commit used to build it.

Final check

A successful release is not just an uploaded file. It is a tested build, a protected signing process, accurate privacy information and a plan to respond if users encounter problems.
